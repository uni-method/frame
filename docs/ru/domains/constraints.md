# Ограничения

Секция `constraints` и по тому, как ограничения в целом устроены во
фреймворке: что описывается данными, что кодом, и как это сходится в рантайме.

## Термины и место в архитектуре

**Ограничение (constraint)** — предикат над _субъектом_ в _контексте_ с
объявленным _исходом_. Валидация — частный случай: субъект = объект, собранный из
входа клиента, исход = накапливаемое нарушение (422). Другие исходы той же
природы:

| Исход       | Код                   | Кто                             | Пример                                  |
| ----------- | --------------------- | ------------------------------- | --------------------------------------- |
| `violation` | 422                   | накапливается, отдаётся списком | пустое имя, email не email              |
| `deny`      | 403                   | прерывает, ровно одна ошибка    | объект принадлежит другому пользователю |
| `missing`   | 404                   | прерывает                       | ссылка на несуществующую сущность       |
| `reject`    | 400                   | прерывает                       | незаявленный фильтр, кривой JSON        |
| `misconfig` | ошибка прибилда / 500 | не доходит до клиента           | правило неприменимо к типу              |

Поэтому в именовании фреймворк говорит об **ограничениях**, а не о валидаторе:
`ConstraintCheckerInterface`, `ConstraintContext`, `ConstraintPhase`
(см. «Проверка ограничений в рантайме» ниже).

**Секция `constraints` — не часть рабочей части фреймворка.** Это
языконезависимая спецификация, которую читает **прибилд**: вместе со `schema`
и `types` она описывает контракт, а прибилд порождает из неё рабочий конфиг и
нативный артефакт проверки для целевого языка (сейчас — PHP/Symfony Validator,
дальше — другие цели). Рантайм фреймворка о `constraints` не знает — он знает
только адаптер `ConstraintCheckerInterface`, который делегирует нативному
валидатору цели.

Разделение ответственности с другими механизмами:

- **Caster** гарантирует вид значения («это int»). Правила начинаются там, где
  Caster заканчивается: «этот int в диапазоне».
- **`writable`** (schema) — можно ли писать поле. Правила — что именно можно
  записать.
- **`|null` в type-спеке** — может ли значение отсутствовать в хранении.
  Правило `notNull` — запрет null на входе (обычно контекстный).
- **`access`** (schema, на действии/пути/операторе) — грубый фильтр «кто вообще
  может дёргать ручку». Ограничения — тонкая проверка над конкретным объектом.

## Структура секции

```yaml
constraints:
  user: # ключ — тип модели из schema.models
    attributes:
      email: # ключ — имя атрибута из schema
        rules: [email, { type: length, max: 255 }]
        create: [notBlank]
      tags: # string[]
        rules: [{ type: count, max: 10 }]
        each: [{ type: length, max: 30 }]
    relations:
      author: # manyToOne
        create: [notNull]
      orders: # oneToMany
        rules: [{ type: count, max: 100 }]
```

Четыре группы правил у свойства:

| Группа   | Когда действует                                         |
| -------- | ------------------------------------------------------- |
| `rules`  | всегда (базовые)                                        |
| `create` | **дополнительно** к базовым в действии create           |
| `update` | **дополнительно** к базовым в действии update           |
| `each`   | к каждому элементу list-типа (только скалярные массивы) |

Семантика слияния — **добавление, не замена**: в create проверяются
`rules + create`. Переопределять одно правило разными параметрами в базовой и
контекстной группе не нужно и не поддерживается.

`each` для связей запрещён: элементы `*ToMany`-связи — модели, целевая модель
валидируется по собственному блоку `constraints`.

## Форма записи правила

Короткая форма — голое имя, полная — объект с параметрами, «расплющенными» на
верхний уровень (по образцу операторов фильтров):

```yaml
rules:
  - notBlank # без параметров
  - { type: length, min: 2, max: 64 } # с параметрами
```

## Каталог правил

Каталог закрыт и хранится данными в `resources/constraint-rules.json` — из него
читают прибилд и редактор.

| Правило       | Область   | Применимо к                  | Параметры      |
| ------------- | --------- | ---------------------------- | -------------- |
| `notNull`     | значение  | любой nullable-тип; связи    | —              |
| `notBlank`    | значение  | string                       | —              |
| `length`      | значение  | string                       | `min?`, `max?` |
| `regex`       | значение  | string                       | `pattern`      |
| `email`       | значение  | string                       | —              |
| `url`         | значение  | string                       | —              |
| `range`       | значение  | int, float, datetime         | `min?`, `max?` |
| `choice`      | значение  | string, int, uuid            | `values`       |
| `equals`      | значение  | string, int, bool, uuid      | `value`        |
| `count`       | коллекция | любой list-тип; toMany-связи | `min?`, `max?` |
| `uniqueItems` | коллекция | string[], int[], uuid[]      | —              |

Политика каталога: правило попадает в него, только если выразимо **во всех
целях** прибилда. Правило одной цели — либо расширение `x-<target>:` в
спецификации, либо локальный код (см. «Граница спецификации и локального кода»).

Типовой кейс `equals` — согласие на обработку данных: bool-поле, которое при
создании обязано быть `true`:

```yaml
agreedToTerms:
  create: [{ type: equals, value: true }]
```

## Матрица применимости

Легальность правила на свойстве — функция от разобранного типа
(`TypeSpecParser` → kind / list / nullable) и признака «это связь»:

- правила области **значение** не вешаются на list-тип напрямую — на элемент
  через `each`;
- правила области **коллекция** требуют list-тип;
- `notNull` применим только к nullable-типам (на не-nullable он тавтологичен);
- связь трактуется как тип: `oneToMany`/`manyToMany` — list,
  `manyToOne`/`oneToOne` — nullable-одиночное значение (обязательность — явный
  `notNull`, обычно в `create`);
- на связях допустимы только правила с пометкой «связи» (`notNull`, `count`).

Нарушение матрицы, ссылка на несуществующую модель/свойство, отсутствие
обязательного параметра — ошибки **прибилда** (тексты — в [config.md](config.md),
«Валидация конфига», «Секция constraints»). Ошибки собираются все сразу. До
рантайма такое не доходит.

## Семантика null

Правила значения применяются только к не-null значениям. Если значение null:
единственное, что проверяется — есть ли среди действующих правил `notNull`.
Поэтому `length`/`email` на nullable-поле не требуют значения — они ограничивают
его, _когда оно есть_; обязательность выражается отдельным `notNull`.

Эта семантика фиксируется на уровне спецификации, а не цели: каждая цель обязана
её воспроизвести (для Symfony она совпадает «из коробки» — `Length`, `Email`,
`Range` сами пропускают null).

## Реестр именованных типов (`types`)

Необязательная секция-словарь переиспользуемых типов. Объявленный тип
используется в `type` атрибута наравне со встроенными, включая модификаторы
`[]` и `|null`:

```yaml
types:
  order_status: # enum
    kind: string
    enum: [new, paid, shipped]
  money: # семантический тип поверх int
    kind: int
    rules: [{ type: range, min: 0 }]

schema:
  models:
    order:
      attributes:
        status: { type: order_status }
        total: { type: money }
        prices: { type: "money[]" }
```

Семантика:

- `kind` — хранимый скалярный вид (из встроенных); применимость правил
  наследуется от него (`range` на `money` легален).
- `enum` — закрытый набор значений; работает как неявное правило `choice`,
  повторять его в `constraints` не нужно. Прочие value-правила на enum-типах
  не имеют смысла.
- `rules` — неявные правила типа, действуют всегда и **добавляются** к правилам
  свойства; для list-типов применяются к каждому элементу. Прибилд раскрывает
  их на каждое свойство этого типа.
- `choice` остаётся для одноразового инлайнового набора значений; всё
  переиспользуемое — через `types`.

Привязка PHP-класса (backed enum, value object) — забота `impl`, не этой секции.

## Прибилд и цели

Прибилд читает `schema` + `types` + `constraints` + `impl` и порождает:

1. рабочий конфиг фреймворка (`schema` + `impl`; секции `constraints` в нём
   уже нет);
2. нативный артефакт проверки для цели — для PHP это метаданные Symfony
   Validator;
3. (побочный выигрыш той же спецификации) JSON Schema / OpenAPI
   (`minLength`, `pattern`, `format: email`, `minimum`, `enum`, `minItems`,
   `uniqueItems` — отображение один-в-один), клиентскую валидацию, подсказки
   DDL (`length.max` → `varchar(n)`, `notNull` → `NOT NULL`).

### Цель PHP / Symfony Validator

Генерировать атрибуты на сущности **нельзя** — это ручной код, регенерация его
затрёт. Нужный механизм уже есть в Symfony Validator: метаданные класса
собираются `LoaderChain` из нескольких источников. Поэтому артефакт прибилда —
отдельный источник метаданных (сгенерированный `validation.generated.yaml` или
кастомный `LoaderInterface`, читающий спецификацию напрямую; выбор между ними
открыт), а локальные `Assert\*` остаются атрибутами на классах. Оба источника
сливаются в один набор метаданных **без слияния кода**: сгенерированный файл
никогда не правится руками, атрибуты никогда не повторяют правила спецификации.

Таблица соответствия для Symfony:

| Спецификация               | Symfony                                    |
| -------------------------- | ------------------------------------------ |
| `notNull`                  | `NotNull`                                  |
| `notBlank`                 | `NotBlank`                                 |
| `length`                   | `Length`                                   |
| `regex`                    | `Regex`                                    |
| `email`                    | `Email`                                    |
| `url`                      | `Url`                                      |
| `range`                    | `Range`                                    |
| `choice`, `types.*.enum`   | `Choice`                                   |
| `equals`                   | `IdenticalTo`                              |
| `count`                    | `Count`                                    |
| `uniqueItems`              | `Unique`                                   |
| `each: [...]`              | `All([...])`                               |
| `types.*.rules`            | раскрываются на каждое свойство этого типа |
| группа `create` / `update` | группа валидации `create` / `update`       |
| группа `rules`             | `Default`                                  |

Контекст действия проецируется в группы валидации с фиксированными именами —
это мост между сгенерированным и локальным слоем (см. «Рантайм: фазы и контекст» и
[usage/validation-patterns.md](../usage/validation-patterns.md)).

### Что нужно от `impl` для генерации

Symfony-метаданные адресуют `properties` или `getters`, а impl хранит имена
getter/setter. Правило вывода: публичное свойство → `properties`, метод
`getX`/`isX` → `getters: x`; если вывести нельзя — явное поле
`validationTarget` в impl-атрибуте.

### Конформанс

Корректность привязки тестируется не по проектам, а конформанс-набором:
фикстура спецификации + ожидаемые нарушения, прогоняемая против каждой цели.
У каждой цели в документации привязки — таблица соответствия (как «Цель PHP / Symfony Validator») и
перечень расхождений с семантикой спецификации.

## Граница спецификации и локального кода

Модель — **один контракт с двумя равноправными источниками правил**: данные
(`constraints`) и код (`Assert\*`, свои констрейнты). Ни один из них не «легаси».
Централизуется не объявление, а то, что иначе расходится: формат нарушения,
контекст, порядок, исход.

Правило разграничения — не «просто/сложно», а **замыкание на схему**:

- правило параметризуется только типом/путём из схемы и литералами → **данные**
  (`constraints`);
- правило ссылается на `this`, другое свойство, выражение, окружение
  (пользователь, БД, предыдущее состояние) → **код**.

Для кода `Expression`, `When`, `Callback`, `GroupSequence`, цепочки «зона того
же огорода» — естественная форма; переносить их в YAML нет смысла. Готовые формы
кодовых правил — [usage/validation-patterns.md](../usage/validation-patterns.md).

Обязательства обоих слоёв:

1. Одна форма нарушения: путь (`source.pointer`), сообщение, исход.
2. Один контекст: действие → группы валидации с фиксированными именами.
3. Один порядок: Caster → сгенерированный слой → локальный слой → сейвер, с
   семантикой `GroupSequence` между слоями (непустой результат слоя
   останавливает следующий). Код вправе не гардить то, что уже гарантировал
   сгенерированный слой (`notNull`, `choice`, диапазон).
4. Запрет дублирования предиката: одно правило живёт ровно в одном слое.
   Прибилд это не поймает — пункт чеклиста ревью.

Цена: спецификация самодокументируема (редактор, OpenAPI), код — нет. Либо в
описании действия честно «плюс доменные правила, см. класс», либо (отдельное
решение) `describe(): string` на своих констрейнтах для генерации документации.

## Рантайм: фазы и контекст

Фреймворк вызывает `ConstraintCheckerInterface::check(object, ConstraintContext)`
в трёх фазах (`ConstraintPhase`):

| Фаза          | Когда                                                 | Объект                | Действия                                                            |
| ------------- | ----------------------------------------------------- | --------------------- | ------------------------------------------------------------------- |
| `AfterLocate` | объект получен локатором, вход ещё не применён        | сущность из хранилища | read, update, delete; резолв `reference` в `writable` — планируется |
| `AfterInput`  | объект собран из входа и прошёл мутаторы `afterInput` | сущность / DTO        | create, update                                                      |
| `ListQuery`   | DTO list-запроса собран                               | `{Model}ListRequest`  | list                                                                |

`ConstraintContext` несёт `modelType`, `actionType`, `phase`, текущего
пользователя (`user`), `id` из запроса (read/update/delete) и `original` —
снимок объекта до применения входа (только update в `AfterInput`):
поверхностный clone сущности — скаляры достоверны, связи те же инстансы;
подробнее — «Проверка ограничений в рантайме» ниже.

Пайплайн по действиям:

- read: locate → `AfterLocate` → include → output
- update: locate → `AfterLocate` → маппинг входа → `AfterInput` (с `original`)
  → saver
- delete: locate → `AfterLocate` → remover
- create: маппинг входа → `AfterInput` → saver
- list: маппинг query → `ListQuery` → repository

`AfterLocate` — та фаза, которой раньше не было: проверить «можно ли этому
пользователю этот объект» можно было только кастомным локатором. Теперь это
ограничение на классе сущности с группой действия (пример —
[usage/validation-patterns.md](../usage/validation-patterns.md), паттерн 7). Два следствия:

- `list` этой фазой не покрывается принципиально: пост-фильтрация выборки —
  утечка через пагинацию и `total`. Для списков владение — обязательный фильтр
  или репозиторий.
- Отказ на чтении раскрывает существование записи; если это важно, нужна
  опция «отвечать 404 вместо 403» (планируется).

Результат `check` — `Error[]` (накопленные `violation`); прерывающие исходы
(403/404) — доменным исключением из реализации. Код ответа выводится из самих
`Error` (все одного статуса → он; иначе 400).

## Проверка ограничений в рантайме (ConstraintCheckerInterface)

Фреймворк не проверяет бизнес-правила сам — он делегирует это вашему адаптеру,
но сам решает **когда** и **с каким контекстом** его вызвать.

```php
interface ConstraintCheckerInterface
{
    /** @return array<\UniMethod\Frame\Integration\Error> */
    public function check(object $object, ConstraintContext $context): array;
}
```

Пустой массив — нарушений нет. Непустой — фреймворк превращает его в
`ApiResult::errors(...)`; HTTP-код выводится из самих `Error` (все одного статуса
— он и берётся, иначе 400). Прерывающие исходы (403/404) адаптер бросает
доменным исключением (см. [errors.md](errors.md)) — валидация прерывается, в ответе ровно одна
ошибка.

### Фазы

```php
enum ConstraintPhase: string
{
    case AfterLocate = 'afterLocate'; // объект из локатора, вход ещё не применён
    case AfterInput  = 'afterInput';  // объект собран из входа
    case ListQuery   = 'listQuery';   // DTO list-запроса
}
```

Точки вызова по действиям:

| Действие | Вызовы `check`                                                     |
| -------- | ------------------------------------------------------------------ |
| read     | `AfterLocate` на найденной сущности                                |
| update   | `AfterLocate` на найденной сущности → маппинг входа → `AfterInput` |
| delete   | `AfterLocate` на найденной сущности                                |
| create   | `AfterInput` на собранной сущности/DTO                             |
| list     | `ListQuery` на `{Model}ListRequest`                                |

`AfterInput` выполняется после мутаторов фазы `afterInput` и до `afterValidate`.
Непустой результат любой фазы останавливает пайплайн: при провале `AfterLocate`
в update маппинг входа и сейвер не вызываются; при провале `AfterInput` —
мутаторы `afterValidate` и сейвер.

Если локатор вернул `null`, `check` не вызывается — ответ 404 формируется до
него.

### Контекст

```php
final readonly class ConstraintContext
{
    public string $modelType;        // тип модели из schema.models
    public ActionType $actionType;   // create | read | list | update | delete
    public ConstraintPhase $phase;
    public ?UserInterface $user;     // из UserProviderInterface, null без провайдера
    public string|int|null $id;      // id из запроса (read/update/delete); null для create/list
    public ?object $original;        // поверхностный clone сущности до применения входа; только update в AfterInput
}
```

`original` — поверхностный `clone` найденной сущности, сделанный до маппинга
входа. Скаляры и value-объекты (`DateTime`) «до» в нём достоверны; связанные
объекты и коллекции — те же инстансы, что и в текущем (сравнивайте их по id,
не по полям). Это сущность, а не DTO: правила читают её теми же геттерами,
что и текущий объект (`UnchangedOnUpdate` в Symfony-бандле делает именно так).
Нужен правилам вида «поле нельзя менять после создания», «переход статуса
допустим». Найденный объект маппер после этого мутирует на месте — второго
запроса в хранилище не делает.

Фабрики: `ConstraintContext::afterLocate(...)`, `::afterInput(...)`,
`::listQuery(...)` — ими пользуется `ApiService`; в своём коде контекст
создавать не нужно.

### Адаптер

Адаптер — мост к вашей библиотеке (Symfony Validator и т.п.): прогоняете объект
через её правила, маппите нарушения в `Error(status, detail, title?, source?)`.
Контекст используется для выбора правил: действие и фаза проецируются в группы
валидации с фиксированными именами (контракт моста — в
[usage/validation-patterns.md](../usage/validation-patterns.md), «Фазы и группы»).

```php
final class SymfonyConstraintChecker implements ConstraintCheckerInterface
{
    public function __construct(private ValidatorInterface $inner) {}

    public function check(object $object, ConstraintContext $context): array
    {
        $groups = match ($context->phase) {
            ConstraintPhase::AfterLocate => [$context->actionType->value],
            ConstraintPhase::AfterInput  => ['Default', $context->actionType->value],
            ConstraintPhase::ListQuery   => ['Default'],
        };

        $errors = [];
        foreach ($this->inner->validate($object, null, $groups) as $violation) {
            $errors[] = new Error(
                Errors::ENTITY_VALIDATION_ERROR_CODE,
                (string) $violation->getMessage(),
                'Validation errors',
                ['pointer' => $violation->getPropertyPath()],
            );
        }

        return $errors;
    }
}
```

Разница между «вернуть `Error[]`» и «бросить доменное исключение»: верните
`Error[]` для ожидаемых нарушений конкретного объекта (их может быть несколько
сразу); доменное исключение — для прерывающих исходов (доступ, не найдено).
Правило, которое неприменимо к объекту (путь не существует, значение по пути не
того вида), — ошибка конфигурации: бросайте исключение с маркером
`FrameConfigurationException`, а не пропускайте проверку молча (см. [errors.md](errors.md)).

## Планируется

Не реализовано; описано, чтобы новые правила ложились в ту же модель, а не
плодили локальный код там, где форма повторяется на каждой сущности.

- `message` в дескрипторе правила (текст — часть контракта) и заполнение
  `source.pointer` адаптером.
- Правила уровня модели: `constraints.<model>.rules` — `oneOf`, `allOrNone`.
- Правила относительно `original` в update: `unchanged`,
  `transition: {from, to}`, `immutableWhen`.
- Правила на связи, параметризуемые путями: `exists`, `sameParent`,
  `ownedBy: path` (+ `exceptRoles`), `targetState`.
- `unique` / `uniqueBy: [a, b]` вместо кода сейвера или 500 из индекса.
- Предусловия `delete`: `noChildren`, запрет по статусу.
- Read-сторона: правила на значения фильтра в `config.filters`
  (`rules: [{type: count, max: 50}]`), минимальная длина для `like`.
- `on: [read, update, delete]` у правила — явный выбор фаз; прибилд раскрывает
  в группы.
- `AfterLocate` для `reference` в `writable` (внутри `MappingToObject`).
- Опция `denyAs: 404`.
- `impl.constraintRules: { alias: class }` — только для окруженческих правил,
  параметризуемых путями; всё выражение-подобное остаётся локальным кодом.

## Чеклист

- [ ] Имена — ключи объектов; `attributes` и `relations` разделены.
- [ ] Контекстные группы не дублируют базовые правила (merge — добавление).
- [ ] На list-атрибутах: коллекционные правила в `rules`, поэлементные — в `each`.
- [ ] `each` не используется на связях.
- [ ] `notNull` — только на nullable-типах и toOne-связях (чаще в `create`).
- [ ] Переиспользуемые наборы значений — в `types`, а не `choice` по месту.
- [ ] Правило, замкнутое на схему, — в `constraints`; правило с `this`/окружением
      — в коде. Один предикат — в одном слое.
- [ ] Сгенерированный артефакт не правится руками.
- [ ] Прибилд проходит: матрица применимости, ссылки на модели/свойства,
      обязательные параметры правил, поддержка правил выбранной целью.
