# Выбор стратегии сохранения: что где используем

Документ о том, как сущность/модель попадает в хранилище и как выбрать способ под бизнес-задачу. Речь про связку `entityLocator` + `entitySaver` пишущего экшена и про то, нужна ли отдельная модель запроса вместо прямого маппинга на ORM-сущность.

## Картина в целом

Любой пишущий экшен (`create`/`update`) собирается из двух частей:

- **entityLocator** — как найти существующий объект (для `update`) или подготовить новый. Чаще всего стандартный ORM-локатор, реже кастомный (например для DTO над несколькими сущностями). Локатор отвечает только на «найти по id»; «можно ли этому пользователю этот объект» — ограничение на классе сущности, которое фреймворк проверяет в фазе `AfterLocate` сразу после локатора ([validation-patterns.md](validation-patterns.md), паттерн 7).
- **entitySaver** — что сделать с присланными данными. Либо декларативный ORM-сейвер (разложить поля по сущности и зафиксировать), либо кастомный сейвер с бизнес-логикой.

Выбор определяется одним вопросом: **совпадает ли «сохранить» с «разложить присланные поля по колонкам и зафиксировать»?** Если да — стандартный ORM-сейвер. Если между входом и состоянием БД есть преобразование, побочный эффект или правило — кастомный сейвер, и почти всегда вместе с ним отдельная модель запроса.

## Три стратегии

### A. Прямой ORM-маппинг (сущность = модель)

Стандартный локатор + стандартный сейвер. Модель указывает прямо на ORM-сущность, геттеры/сеттеры — это методы сущности.

Когда: CRUD без логики. Клиент шлёт поля → они ложатся в строку → фиксация. Ответ — та же сущность как есть. Связи передаются как ссылки.

Типовые случаи: справочники, простые доменные сущности, которые редактируются «как есть» без пересчётов и побочных эффектов.

### B. Кастомный сейвер над ORM-сущностью

Стандартный локатор + кастомный сейвер, но модель по-прежнему может маппиться на сущность. Сейвер инкапсулирует доменную операцию: пересчёт, каскад, запись истории, переход статуса.

Когда: данные ложатся в существующие сущности, но через нетривиальную процедуру.

Типовые случаи: переходы по конечному автомату статусов с записью в журнал; сохранение записи, которое тянет пересчёт связанных агрегатов; массовая вставка набора строк из одного запроса.

### C. DTO запроса + кастомный сейвер (модель ≠ сущность)

Отдельная модель запроса, не ORM-сущность. Сейвер сам строит/находит сущности, выполняет побочные эффекты и пишет вычисленные значения обратно в модель для ответа.

Когда: контракт запроса/ответа не совпадает со структурой таблицы — вычисляемые поля в ответе, расхождение набора полей, доменные правила с управляемыми HTTP-кодами, несколько затронутых сущностей. Подробно — в [create-dto.md](create-dto.md).

Типовые случаи: аутентификация и выдача токена; смена/сброс пароля; создание пользователя с генерацией пароля и разворачиванием полей; запрос-вычисление, который возвращает рассчитанный результат, не сохраняя сам запрос.

## Таблица сравнения

|                              | A. Прямой ORM                     | B. Кастомный сейвер над сущностью | C. DTO + кастомный сейвер     |
| ---------------------------- | --------------------------------- | --------------------------------- | ----------------------------- |
| Модель маппится на           | ORM-сущность                      | ORM-сущность                      | отдельный POPO-модель запроса |
| entitySaver                  | стандартный                       | кастомный                         | кастомный                     |
| Вход = структура таблицы     | да                                | да (в основном)                   | нет                           |
| Вычисляемые поля в ответе    | нет                               | редко                             | да                            |
| Побочные эффекты             | нет                               | да                                | да                            |
| Доменные правила → HTTP-коды | нет (только БД-ограничения → 500) | да                                | да                            |
| Несколько сущностей за раз   | нет                               | возможно                          | часто                         |
| Стоимость поддержки          | минимальная                       | средняя                           | высокая                       |

## Как выбрать

Дефолт — стратегия A; кастомный сейвер — крайняя мера, для него нужен серьёзный довод. Почти всё, что на первый взгляд «требует сейвера», разруливается декларативными средствами фреймворка:

- запись связей — `writable: {x: reference}` в конфиге + декларация `?included=x` и ссылка `{"x": {"id": …}}` в теле (фронт готовит связи и шлёт ссылки; несколько сущностей = несколько запросов, а не один сейвер над всеми);
- создание связанной сущности вместе с корневой — `writable: {x: create}`, а если связь должна принимать и ссылку по `id`, и новый объект — `reference_or_create` (плюс `cascade: ['persist']` и `Assert\Valid` на свойстве сущности);
- валидация входа — секция `constraints` конфига (правила по типу: обязательность, длины, форматы, словари) плюс `Assert\*`-атрибуты на сущности для правил с `this`/окружением; фреймворк прогоняет и то и другое до сохранения и отдаёт 422 без единой строки кода в сейвере;
- доступ к объекту по владельцу/роли на read/update/delete — констрейнт с группами действий (фаза `AfterLocate`), не кастомный локатор;
- скрытие/преобразование полей — мутаторы (`hide`, `hasher` и т.п.);
- вычисляемые связи в ответе — Criteria-геттер или relationMutator (см. [list-action.md](list-action.md)).

Только если задача не закрывается этим набором, идти сверху вниз — первый сработавший пункт даёт ответ:

1. Ответ содержит значение, которого не было во входе и которое не лежит в сущности один-к-одному (сгенерированный секрет, токен, вычисленный результат)? → **C**.
2. Набор входных полей структурно расходится с сущностью (одно поле разворачивается в массив; «виртуальная» сущность над несколькими таблицами)? → **C**.
3. Есть доменное правило, которое должно давать осмысленный код (422 на нарушение уникальности вместо 500; 403 на отсутствие прав)? → если правило про контракт запроса — **C** (валидатор модели + проверки в сейвере); если про процедуру над существующими сущностями — **B**.
4. Сохранение тянет за собой побочный эффект — запись истории, пересчёт связанных строк, каскад, отправку уведомления, массовую вставку? → **B**.
5. Ничего из перечисленного, «принять поля и сохранить»? → **A**.

## Антипаттерны

- **Сейвер там, где хватает декларативных средств.** Проверка формата поля — Assert-атрибут на сущности; секрет в ответе — мутатор `hide`; запись связи — reference + `?included`; вычисляемая связь — relationMutator. Сейвер ради любого из этих пунктов — лишний слой кода, тестов и конфигурации.
- **Сейвер ради «id или новый объект».** Выбор между ссылкой и созданием делает режим `reference_or_create`: ветка определяется формой полезной нагрузки, кастомный код для этого не нужен.
- **Сейвер ради уникального ограничения — по обстоятельствам, не рефлекторно.** Дубль по уникальному индексу без проверки в сейвере улетит в 500 вместо 422. Осознанный компромисс — оставить уникальность на индексе БД, если UI исключает дубли (прецеденты: `resourceCountry` прячет привязанные страны в селекте, `whitelabelCredential` — пара кабинет+вайтлейбл). Проверка в сейвере оправдана, когда 422 нужен как часть контракта (занятый email при создании пользователя).
- **Доменные проверки в БД-ограничениях вместо сейвера.** Ограничение защищает целостность, но не даёт нормального доменного ответа. Бизнес-правило живёт в сейвере/валидаторе.
- **Кастомный локатор ради проверки доступа.** «Отдать объект автору и админу, остальным ошибка» — не задача поиска по id. Для этого есть фаза `AfterLocate`: констрейнт на классе с `groups: ['read', 'update', 'delete']`, стандартный ORM-локатор остаётся. Локатор, возвращающий `null` для чужого объекта, — только осознанный выбор «404 вместо 403», и то временный (опция планируется в фреймворке).
- **Новая модель ради одной CRUD-сущности без логики.** Если создание тривиально, отдельный DTO — лишний код и лишний маппинг. Используйте A.
- **Технические исключения как клиентские ошибки.** Исключение о рассогласовании сейвер↔модель не доменное и означает ошибку конфигурации → 500: оно реализует `FrameConfigurationException`, а не `FrameDomainException`. Для входных ошибок клиента — доменные исключения валидации/доступа с корректными кодами.
