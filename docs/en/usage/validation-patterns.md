# Constraint patterns: what to put in right away

A catalog for writing a new entity, DTO or action. There is one rule: a check lives in a constraint on the object, a saver is only for side effects, a locator is only for lookup by id. The choice of a persistence strategy is in [persistence-strategy.md](persistence-strategy.md), the boundary between rules in the config's `constraints` and rules in code is in [domains/constraints.md](../domains/constraints.md) ("The boundary between the specification and local code"), here are ready-made forms for each type of rule in code.

Two layers of rules on one class:

- **generated by the prebuild** from the `constraints` section (being required, lengths, formats, dictionaries, ranges) — they come as a separate Symfony Validator metadata source and are **not repeated** with attributes;
- **local** — `Assert\*` attributes and your own constraints for everything that refers to `this`, another property, the user, the DB, the previous state.

Pattern 1 (being required, dictionaries) is shown with attributes for projects without the prebuild; when the `constraints` section exists, they are written there, and patterns 2–13 remain in code.

## What is never written in a saver and a locator

- being required, dictionaries, formats;
- consistency of relations (a variety of the same crop, a zone of the same garden);
- conditional requiredness and prohibitions by state;
- belonging to the current user and rights by role — including for **reading and deletion**;
- immutability of a field after creation;
- aggregate conditions over the object's relations.

All of this is attributes on the entity/DTO with the message the client expects. A saver remains only when there is a side effect, an upsert, a selection from the DB or an object that the saver chooses itself. A custom locator for the sake of "the author and the admin may, others may not" is not written: this is pattern 7 with action groups.

## Phases and groups

The framework calls the adapter (`ConstraintCheckerInterface`) in three phases and passes the context: the action, the phase, the current user, the id, a snapshot of the object before changes ([domains/constraints.md](../domains/constraints.md), "Runtime constraint checking"). The Symfony bridge projects the context into validation groups — this is the only contract the attributes rely on:

| Phase         | Actions              | Groups                  | Object                               |
| ------------- | -------------------- | ----------------------- | ------------------------------------ |
| `AfterLocate` | read, update, delete | `[<action>]`            | entity from the DB, input not yet applied |
| `AfterInput`  | create, update       | `['Default', <action>]` | entity/DTO after input is applied    |
| `ListQuery`   | list                 | `['Default']`           | `{Model}ListRequest`                 |

Consequences:

- A constraint **without** `groups` lives in `Default` and runs only in `AfterInput`/`ListQuery` — it is not run on a stored object when reading, so records with outdated data do not fail with 422 on `read`.
- The rule "who is allowed this object" is marked with action groups: `groups: ['read', 'update', 'delete']`. In `update` it runs **before** input is applied, on the state from the DB.
- A rule needed only on creation/modification — `groups: ['create']` / `groups: ['update']` (an analog of `create:`/`update:` in the `constraints` section).
- A non-empty result of a phase stops the pipeline: if `AfterLocate` fails, the input is not mapped and the saver is not called.
- `list` is not covered by the `AfterLocate` phase: ownership in a list is a required filter by the user or the repository, not post-filtering.
- A denial in `AfterLocate` on `read` returns 403 and thereby confirms the existence of the record. If this is a leak — for now only a custom locator returning `null`; the option "403 as 404" is planned.

## 1. Being required and dictionaries

```php
#[ORM\Column(length: 32)]
#[Assert\NotBlank(message: 'Select the zone type')]
#[Assert\Choice(choices: self::TYPES, message: 'Select the zone type')]
private ?string $zoneType = null;

#[ORM\ManyToOne(targetEntity: Garden::class)]
#[ORM\JoinColumn(nullable: false)]
#[Assert\NotNull(message: 'Specify the garden')]
private ?Garden $garden = null;
```

- Lists of values are `self::TYPES` constants on the entity, `Choice` refers to them.
- A string from a DTO where spaces = empty: `NotBlank(normalizer: 'trim')`.
- The message is part of the contract and is set right away; default English texts are acceptable only for technical fields that the client does not fill.

## 2. Consistency of two relations

The relation must belong to the same parent as the object:

```php
#[Assert\Expression(
    'value === null or this.getGarden() === null or value.getGardenId() === this.getGarden().getId()',
    message: 'The zone belongs to another garden',
)]
private ?GardenZone $gardenZone = null;
```

- Each step of the chain is guarded against `null` — calling a method on `null` in ExpressionLanguage throws an exception.
- Identifiers are compared (`getXId()`), not objects.
- For a relation one step up (a rule → the marker's planting): `'value === null or this.getPlanting() === null or not value.isCustom() or value.getPlantingId() === this.getPlanting().getId()'`.

## 3. A conditionally required field

```php
#[Assert\When(
    expression: 'this.getPlantingMethod() === seeds',
    values: ['seeds' => self::METHOD_SEEDS],
    constraints: [new Assert\NotNull(message: 'The "Sowing date" field is required for the selected growing method')],
)]
private ?DateTimeImmutable $sownAt = null;
```

- Constants are passed via `values`, literals are not written into the expression string.
- A set of values — `'this.getPlantingMethod() in planted'` with `values: ['planted' => [...]]` (`in` compares values, not keys).
- One rule — one `When`; several fields under one condition — a `When` on each field.

## 4. Either A or B

Two class-level `Expression`s, one for each error text:

```php
#[Assert\Expression(
    'this.getCareProgramVersion() === null or this.getPlanting() === null',
    message: 'A rule belongs either to a program version or to a planting',
)]
#[Assert\Expression(
    'this.getCareProgramVersion() !== null or this.getPlanting() !== null',
    message: 'Specify a program version or a planting',
)]
class CareRule
```

A single XOR with a common message is not written: the client must see which of the two rules is violated.

## 5. Prohibition by state

The action is not allowed with a certain status of the object or of a relation:

```php
#[Assert\When(
    expression: 'this.getStatus() === done',
    values: ['done' => self::STATUS_DONE],
    constraints: [new Assert\IsNull(message: 'A completed task cannot be moved')],
)]
private ?DateTimeImmutable $movedToDate = null;

#[Assert\Expression(
    expression: 'value === null or value.getSetupStatus() !== completed',
    values: ['completed' => Garden::SETUP_COMPLETED],
    message: 'The garden setup is already completed',
)]
public Garden|null $garden = null;
```

The entity's status methods (`isSetupAtLeast`, `isCustom`, `isActive`) are called directly from the expression — that is their purpose.

## 6. Dates

```php
#[Assert\GreaterThanOrEqual('today', message: 'A task cannot be moved to the past')]
private ?DateTimeImmutable $movedToDate = null;
```

The input string is parsed into `DateTimeImmutable` in the setter; constraints are put on the typed property, not on the string. An invalid date gives `null` → caught by `NotNull`.

## 7. The owner is the current user

On each entity belonging to a user, a class-level `OwnedByCurrentUser` with a path to `User` and the groups of all actions where ownership is checked:

```php
#[OwnedByCurrentUser(
    path: 'user',
    message: 'The garden belongs to another user',
    groups: ['read', 'update', 'delete'],
)]
class Garden

#[OwnedByCurrentUser(
    path: 'garden.user',
    message: 'The planting belongs to another user',
    groups: ['read', 'update', 'delete'],
)]
class Planting
```

- The path always goes to the user, not to their id.
- `null` on the path is skipped: being required is a separate `NotNull`, and the owner of the root entity is set by the saver/mutator.
- A violation is `AccessDeniedException` (403), not a violation (422); see "Response codes".
- The message text is uniform across the project for each object type ("The garden belongs…", "The planting belongs…").
- The groups are the actions on which the object already exists (`read`, `update`, `delete`): the check runs in the `AfterLocate` phase, on the object from the DB. `create` is not included — the owner of a new object is set by the saver/mutator, and someone else's relation on creation is caught by pattern 2.
- An exception for a role ("the author and the admin") is a constraint parameter, not a second rule:

```php
#[OwnedByCurrentUser(
    path: 'author',
    exceptRoles: [User::ROLE_ADMIN],
    message: 'The post belongs to another user',
    groups: ['read', 'update', 'delete'],
)]
class Post
```

This is exactly the replacement for a custom locator: `entityLocator: doctrine`, an attribute on the class, a feature test for 403 for another user and 200 for the author and the admin.

## 8. A field only for a role

```php
#[HasRole(User::ROLE_ADMIN, message: 'Only an administrator can edit a care program rule')]
private ?CareProgramVersion $careProgramVersion = null;
```

A filled value requires the role, an empty one is skipped. The coarse filter "who can call the endpoint at all" is `access.roles` in the config; `HasRole` is for fields that are available to different roles in one action.

## 9. Immutable after creation

```php
#[Assert\NotNull(message: 'Specify the garden')]
#[UnchangedOnUpdate(message: 'A zone cannot be moved to another garden', groups: ['update'])]
private ?Garden $garden = null;
```

The `update` group — the rule makes sense only in `AfterInput` on modification; the validator takes the "before" value from `ConstraintContext::$original` (a snapshot before input is applied), not from the UnitOfWork.

At the same time the relation **remains** in `writable` of `update` — otherwise the client gets the framework's generic "Relation ... is not writable" instead of the domain text. Remove the field from `writable` only when it cannot be sent at all and the error text does not matter.

## 10. An aggregate over relations

A condition with a loop over a collection is a `Callback` with a named method, the violation is bound to the trigger field:

```php
#[Assert\Callback('validateCompletion')]
final class GardenSetup
{
    public function validateCompletion(ExecutionContextInterface $context): void
    {
        if ($this->complete !== true || !$this->garden instanceof Garden) {
            return;
        }

        foreach ($this->garden->getPlantingsAsArray() as $planting) {
            $stage = $planting->getCurrentStage();
            if (!$stage instanceof PlantingStage || $stage->getConfirmedAt() === null) {
                $context
                    ->buildViolation('The stage of the planting "{{ planting }}" is not confirmed')
                    ->setParameter('{{ planting }}', $planting->getCustomName() ?? (string) $planting->getCrop()?->getName())
                    ->atPath('complete')
                    ->addViolation();
            }
        }
    }
}
```

Conditions without a loop (`getNotificationPreferences() !== null`, `getPlantingsAsArray() != []`) — regular `Expression`s inside `When`.

## 11. A wizard step DTO with a nested entity

The DTO sends a nested entity without a parent (the saver will set the parent). A regular `Valid` would fail the parent's `NotNull`, so this is put in right away:

```php
// entity
public const string GROUP_SETUP = 'setup';

#[Assert\NotNull(message: 'Select a crop', groups: ['Default', self::GROUP_SETUP])]
private ?Crop $crop = null;
// … all field checks — in both groups; garden and OwnedByCurrentUser — only Default

// DTO
#[Assert\GroupSequence(['GardenSetup', Planting::GROUP_SETUP])]
final class GardenSetup
{
    #[Assert\Valid(groups: [Planting::GROUP_SETUP])]
    public Planting|null $planting = null;
}
```

- The first element of `GroupSequence` is the short class name of the DTO: all checks of the step itself run in it.
- `Valid` with an explicit group validates the nested object in that group, not in `Default`.
- Checks that need the parent (a zone of the same garden) are duplicated on the DTO via `this.garden`.
- "Which step" is one class-level `Expression` with the list of filled relations and the text "The step is not specified…"; the step checks are `When` on its relation.

## 12. Authentication and registration DTOs

```php
#[Assert\NotBlank(message: "Email and password are required")]
public string|null $email = null;

#[Assert\NotBlank(message: "initData is required", normalizer: 'trim')]
public string|null $initData = null;
```

The saver of such DTOs does not repeat being required: it casts with `(string)` and does its own job — checking credentials (401), activity (403), issuing a token, hashing, creating a user. Email uniqueness on a DTO stays in the saver (`UniqueEntity` works on entities).

## 13. Your own constraint

It is written when the rule depends on the environment: the current user, roles, the previous state, a repository. The criterion from [domains/constraints.md](../domains/constraints.md): everything parameterized only by a type and literals goes into the `constraints` section; everything that refers to `this` or the environment goes here. The form:

```php
#[Attribute(Attribute::TARGET_CLASS)]            // or TARGET_PROPERTY
class OwnedByCurrentUser extends Constraint
{
    public string $message = 'Access denied.';
    public string $path;

    public function __construct(string $path, ?string $message = null, ?array $groups = null, mixed $payload = null)
    {
        parent::__construct([], $groups, $payload);
        $this->path = $path;
        if ($message !== null) {
            $this->message = $message;
        }
    }

    public function getTargets(): string { return self::CLASS_CONSTRAINT; }
    public function validatedBy(): string { return OwnedByCurrentUserValidator::class; }
}
```

The validator:

- dependencies via the constructor (`Security`, `PropertyAccessorInterface`, `EntityManagerInterface`); the current user and the "before" snapshot are also available from `ConstraintContext`, which the bridge puts into the request context service — this is preferable to `Security`/UnitOfWork, since it works the same in all phases;
- first of all an `instanceof` check of the constraint → `UnexpectedTypeException`;
- an empty value — `return`, being required is not its business;
- an unreachable path (a segment is missing, the value at the path is of the wrong kind) is a constraint configuration error, not a `return`: otherwise a typo in `path` silently disables the rule. Throw an exception with the `FrameConfigurationException` marker (in the bundle — `ConstraintPathMisconfiguredException`), the boundary will return a 500;
- 422 — `buildViolation($constraint->message)->setParameter(...)->addViolation()`;
- 403 — `throw new AccessDeniedException($constraint->message)`.

Existing ones: `OwnedByCurrentUser`, `HasRole`, `UnchangedOnUpdate`. Reusing someone else's constraint (for example `MatchIdentity`) is possible only if both the status and the response text match.

## Response codes and order

- The bridge (`ConstraintCheckerInterface` → Symfony Validator) returns violations as 422 with `source.pointer` = the property path. For 403 the validator throws the domain `AccessDeniedException`: validation is interrupted, the response has exactly one error.
- Phases go sequentially and each one stops the next: in `update` first `AfterLocate` (the `update` group, the object from the DB), then `AfterInput` (`Default` + `update`, the object with input applied). A rule from the `update` group without explicit distinction of phases will run twice — on different states of the object; this is fine for access checks and wrong for input checks, so keep input checks in `Default` or distinguish the phase via the context.
- Violations accumulate, an exception discards the accumulated ones. Class-level constraints go before properties, within a level — in declaration order. A throwing constraint is declared after the rules that must win, or is gated by `When`:

```php
#[Assert\When(
    expression: 'this.getCareProgramVersion() === null',
    constraints: [new OwnedByCurrentUser(path: 'planting.garden.user', message: 'The planting belongs to another user')],
)]
```

Here the disputed rule (both a version and a planting) gets a 422 from pattern 4, not a 403 for someone else's planting.

## What remains in the saver

A saver is written only for this, and it contains none of the checks from the patterns above:

- side effects: recalculating related aggregates, advancing a status, displacing old records, snapshots, cascade creation;
- an upsert by a business key;
- checks that need a selection from the DB or an object chosen by the saver itself (the default planting);
- authentication and issuing a token.

If after this list the saver is empty — the action is on `entitySaver: doctrine`, no saver is created.

## Config

- An action without logic: `create: { entityLocator: doctrine, entitySaver: doctrine }`.
- A relation protected by `UnchangedOnUpdate` — in `writable` of `update`.
- A field filled by the server (a snapshot, a status) — `writable: false`; no constraint is put on it (validation runs before the saver).

## Skeleton of a new user entity

```php
#[ORM\Entity]
#[OwnedByCurrentUser(path: 'garden.user', message: 'The planting belongs to another user')]
class Planting
{
    #[ORM\ManyToOne(targetEntity: Garden::class)]
    #[ORM\JoinColumn(nullable: false)]
    #[Assert\NotNull(message: 'Specify the garden')]
    #[UnchangedOnUpdate(message: 'A planting cannot be moved to another garden')]
    private ?Garden $garden = null;

    #[ORM\ManyToOne(targetEntity: GardenZone::class)]
    #[Assert\Expression(
        'value === null or this.getGarden() === null or value.getGardenId() === this.getGarden().getId()',
        message: 'The zone belongs to another garden',
    )]
    private ?GardenZone $gardenZone = null;

    #[ORM\Column(length: 32)]
    #[Assert\NotBlank(message: 'Select the growing method')]
    #[Assert\Choice(choices: self::METHODS, message: 'Select the growing method')]
    private ?string $plantingMethod = null;

    #[ORM\Column(length: 32)]
    #[Assert\Choice(choices: self::STATUSES)]
    private string $status = self::STATUS_ACTIVE;
}
```

## Review checklist for a new entity/action

- [ ] On each required field and relation — `NotNull`/`NotBlank` with a message.
- [ ] Dictionaries — `Choice` over the entity's constants.
- [ ] Each relation that depends on another — `Expression` with guards against `null`.
- [ ] Conditional rules — `When` with constants via `values`.
- [ ] A user entity — `OwnedByCurrentUser` on the class with a path to `User` and `groups: ['read', 'update', 'delete']`; there is no custom locator for the sake of access.
- [ ] Rules closed over the schema are in the `constraints` section, not attributes; no predicate is duplicated in both layers.
- [ ] Fields for a role — `HasRole`; immutable ones — `UnchangedOnUpdate(groups: ['update'])` and the relation in `writable`.
- [ ] 403 constraints are declared after 422 rules or are gated by `When`.
- [ ] Nested entities in a DTO — via `GroupSequence` + `Valid(groups)`.
- [ ] The saver is either absent (`doctrine`) or contains only side effects.
- [ ] A feature test for each rule: the `detail` text matches the `message`; for access rules — on `read`, `update` and `delete` separately.
